# Baltik — Developer Guide

**Baltik** (*Building Applications Linked with TRUST Kernels*) is the
framework for creating projects that extend the TRUST thermohydraulic
platform.  A baltik inherits the full TRUST C++ API, adds its own source
files and test suite, and can introduce new keywords recognised by the trustify
input-file validator.

---

## Prerequisites

A TRUST installation must be available.  Before running any baltik command,
source the TRUST environment:

```bash
source $TRUST_ROOT/env_TRUST.sh
```

---

## Project layout

A baltik lives in a self-contained directory with the following structure:

```
my_baltik/
├── project.cfg          # project descriptor (required)
├── src/                 # C++ source files (.cpp, .h, ...)
├── tests/               # test datasets (.data files)
├── share/               # optional resources
│   └── bin/
│       ├── pre_configure   # hook run before configure (optional)
│       └── post_configure  # hook run after configure (optional)
└── docs/                    # same layout as TRUST's own docs/
    ├── Makefile             # doc build driver (editable)
    ├── content/             # hand-written narrative pages (scanned by INPUT)
    │   ├── main_page.md     # Doxygen home page / @mainpage (editable)
    │   └── demo.md          # starter page — replace with your own
    └── theme/
        └── header.html      # Doxygen HTML header (editable)
```

Files generated by `configure` and not tracked in git:

```
my_baltik/
├── Makefile             # root Makefile (always regenerated)
├── env_<name>.sh        # environment file  (always regenerated)
├── build/               # compiled objects, symlinked sources, trustify output
└── <name>_opt           # compiled executable (optimised)
```

Note: `docs/Doxyfile` is **not** generated by `configure`. It is
created on first `make` inside `docs/` (from a TRUST-side template) and
then left alone — safe to customise and commit. See the
[Doxygen documentation](#doxygen-documentation) section below.

### `project.cfg`

The only mandatory file.  It has two sections:

```ini
# [description] section — required
[description]
name       : my_baltik          # project identifier (no spaces)
author     : My Team
executable : my_baltik          # name of the generated binary
#kernel    : <kernel_name>      # optional: alternative TRUST kernel
#cpp_flags : -Wno-shadow        # optional: extra compiler flags
#ld_flags  : -lxml2             # optional: extra linker flags

# [dependencies] section — optional
[dependencies]
other_lib : /path/to/other_lib  # other baltik this project depends on
```

Lines beginning with `#` are comments.  All `[description]` fields except
`name` are optional.

## Getting started after cloning

The entry point for any baltik is `baltik_build_configure -execute`.  Run it
once from the baltik root after cloning:

```bash
source $TRUST_ROOT/env_TRUST.sh
$TRUST_ROOT/bin/baltik/bin/baltik_build_configure -execute
source env_<name>.sh
make optim
```

### What `baltik_build_configure -execute` does

The command performs two steps:

**Step 1 — generate `./configure`.**
It writes a thin wrapper script `configure` that simply delegates to
`$TRUST_ROOT/bin/baltik/bin/baltik_configure`.  This wrapper is intentionally
trivial: it exists so you have a stable local entry point even if `$TRUST_ROOT`
changes later.

**Step 2 — run `./configure`.**
The `-execute` flag triggers the configure run immediately.  `configure` is
where all the real work happens:

- reads `project.cfg` for the project name, executable name, compiler/linker
  flags, and dependencies
- resolves all dependencies recursively and validates their paths
- creates `build/src/` and symlinks every source file (`.cpp`, `.h`, `.hxx`, ...)
  from TRUST and each dependency's `src/` into it, giving CMake a flat unified
  source tree
- generates the root `Makefile` with all targets (`make optim`,
  `make check_optim`, `make docs`, ...)
- generates `env_<name>.sh` exporting `exec_opt`, `TRUST_TESTS`,
  `project_directory`, and related variables
- runs `share/bin/pre_configure` before sources are symlinked, and
  `share/bin/post_configure` after everything is generated, if those hooks exist

The `docs/` directory itself is **not** created by `configure`; it is
populated once by `trust -baltik` at project creation (or by
`trust -baltik_docs_scaffold` for a pre-existing project) — see
[Doxygen documentation](#doxygen-documentation) below.

Without `-execute`, `baltik_build_configure` only writes the `configure`
wrapper and stops — useful if you want to inspect or patch it before running.

> **Re-running configure:** any time you add source files, change dependencies
> in `project.cfg`, or update TRUST, re-run `baltik_build_configure -execute`
> (or just `./configure` if the wrapper already exists) to regenerate the
> source symlinks and Makefiles.

### Source the environment and build

```bash
source env_<name>.sh   # exports exec_opt, TRUST_TESTS, project_directory, ...
make optim             # compile in optimised mode
make check_optim       # compile + run the full test suite
```

## Installing from a distribution archive

```bash
tar xzf my_baltik.tar.gz
cd my_baltik
$TRUST_ROOT/bin/baltik/bin/baltik_build_configure
./configure
make check_optim
```

To rebuild the archive from the project:

```bash
make distrib        # creates my_baltik.tar.gz
make distrib_git    # same, but includes only files tracked by git
```

## Available make targets

Run `make help` for a live listing.  The main targets are:

| Target | Description |
|---|---|
| `optim` | Compile in optimised mode |
| `debug` | Compile in debug mode |
| `semi_optim` | Compile with `-O3` and assertions enabled |
| `profiling` | Compile with profiling flags |
| `ctest_optim` | Compile + run test suite (optimised) |
| `ctest_debug` | Compile + run test suite (debug) |
| `check_all_optim` | Run baltik tests + dependency tests (optimised) |
| `validation` | Generate validation report (baltik tests only) |
| `all_validation` | Generate validation report (all tests) |
| `trustify` | Build the trustify Python module for keyword validation |
| `trustify_check` | Validate all datasets with trustify |
| `trustify_doc` | Generate the keyword reference (standalone, no Doxygen) |
| `docs` | Build the full HTML documentation (see below) |
| `gui` | Build the GUI (XDATA compilation) |
| `clean` | Remove compiled objects |
| `dist_clean` | Full clean including configure output |
| `distrib` | Build the distribution archive |
| `distrib_git` | Build the archive from git-tracked files |

## Doxygen documentation

### Independence from the build pipeline

The doc build is **fully orthogonal** to the baltik's `./configure` +
`make optim` build. From a fresh baltik tree you can do `cd docs &&
make` without ever having run `./configure`, compiled the project, or
built any test. The only requirement is `$TRUST_ROOT` set in the
environment so the `docs/Makefile` can locate TRUST's shared
includes (`common.mk`, `baltik.mk`) and the bundled doxygen tarball.

The convenience target `make docs` from the baltik root *does*
require `./configure` to have generated the root Makefile, but that's
purely a convenience — the underlying build lives entirely in `docs/`.

### How it works

The baltik's `docs/Makefile` is a thin shim: it sets a few identity
variables (project name, paths) and then `include`s two shared files
from TRUST:

- **`$TRUST_ROOT/docs/common.mk`** — DOXYGEN binary resolution
  (with `TRUST_DOXYGEN_BINARY` override), `install_doxygen`,
  `install_trustify`, and the `run_doxygen` recipe itself (running
  doxygen + post-processing the HTML).
- **`$TRUST_ROOT/docs/baltik.mk`** — `Doxyfile` (generated once
  from the TRUST baltik template if missing), `doxyfile_chain`
  (regenerated from `BALTIK_DEPENDENCIES`), and the baltik-flavoured
  `trustify_doc` target.

This means improvements to the doc pipeline (new post-processors,
updated doxygen version, theming changes) are made once in TRUST's
`docs/` and picked up by every baltik on the next `make` run — no
template re-sync, no per-baltik patch.

### Generated files

Creating a baltik populates `docs/` with:

| File | Regenerated | Notes |
|---|---|---|
| `docs/Makefile` | Once, by `trust -baltik` | Thin shim — most logic is in TRUST's `common.mk` + `baltik.mk`. Safe to edit, but rebuild from the template if you want a clean copy. |
| `docs/Doxyfile` | Once, by first `make` in `docs/` | Generated from the TRUST baltik template; safe to edit and commit. |
| `docs/theme/header.html` | Once, by `trust -baltik` | Safe to edit and commit. |
| `docs/content/main_page.md` | Once, by `trust -baltik` | The `@mainpage`. Safe to edit and commit. |
| `docs/content/demo.md` | Once, by `trust -baltik` | Starter narrative page. Replace with your own pages; add more `.md` files alongside it. |

Per-build artefacts live under `docs/build/` and are wiped by `make clean`:

```
docs/build/
├── generated_content/      ← trustify keyword reference (kw_ref/ + index)
├── html/                   ← doxygen HTML output (open html/index.html)
└── Doxyfile.chain          ← auto-generated INPUT extension for dep baltiks
```

Everything under `build/` is gitignored — do **not** edit those files by
hand; the next `make` overwrites them.

### Building the documentation

```bash
cd docs && make            # from the baltik root - no configure required
```

or (after `./configure`):

```bash
make docs                  # convenience wrapper provided by the root Makefile
```

The output is written to `docs/build/html/index.html`. It covers:

- the full TRUST C++ API
- all baltik C++ source files (and dependency baltiks', via `Doxyfile.chain`)
- an auto-generated keyword reference (see below)

The documentation uses the same styling as the TRUST reference documentation
(doxygen-awesome-css theme). You can customise the page header (logo, GitHub
corner, extra meta tags, ...) by editing `docs/theme/header.html` — see
[Customising the HTML header](#customising-the-html-header) below.

### Using a non-bundled doxygen

The bundled doxygen 1.16.1 is a Linux x86_64 binary unpacked from
`$TRUST_ROOT/externalpackages/`. If it does not run on your machine
(other OS, libc mismatch, ...), point the build at any other doxygen
installation by exporting `TRUST_DOXYGEN_BINARY`:

```bash
TRUST_DOXYGEN_BINARY=$(command -v doxygen) make
```

If you don't have a doxygen at all, see *Building doxygen from
source* in `$TRUST_ROOT/docs/README.md` — three `cmake` commands and
you're done.

The override is implemented in TRUST's `common.mk`, so it works
identically from TRUST's `docs/` and from any baltik's `docs/`.

### Customising the HTML header

`docs/theme/header.html` is generated once (by `trust -baltik`) and never
overwritten by subsequent builds.  You can freely add, remove, or
rearrange HTML around the Doxygen template placeholders
(`$relpath^`, `$treeview`, `$mathjax`, `$searchbox`, `$projectlogo`,
...).  The contract is simply: **leave the `$…` placeholders in place
and keep the file Doxygen-parseable**; everything else is yours.

#### Adding a GitHub corner pointing at your repo

The most common customisation is a "View on GitHub" corner badge
linking to the baltik's own repository.  The TRUST docs ship one in
`$TRUST_ROOT/docs/theme/header.html`; copy it into your baltik:

1. Open `$TRUST_ROOT/docs/theme/header.html` and locate the
   `<!-- GitHub corner -->` block (an `<a> … <svg> … </svg></a>`
   element, ~10 lines starting with `<a href="https://github.com/...`).
2. Paste it into your baltik's `docs/theme/header.html` immediately after
   the opening `<body>` tag.
3. Replace the
   `href="https://github.com/cea-trust-platform/trust-code"` URL
   with your own repository URL, and update the `title=` /
   `aria-label=` attributes if you want.

The SVG inherits its colours from the doxygen-awesome-css theme
variables (`--primary-color`, `--page-background-color`) so it matches
both light and dark modes automatically — no extra CSS needed.

#### Other common tweaks

- **Bottom-left sidebar logo.**  TRUST's header has a
  `<div id="sidebar-logo">` block near the bottom that shows an image
  via raw HTML (`<img src="$relpath^my_logo.png">`).  Copy the block,
  ship your image under `docs/theme/` (alongside `header.html`), and
  point `src=` at its bare file name.  **You must also list that file
  in `HTML_EXTRA_FILES`** in your `Doxyfile`'s user-override block so
  Doxygen copies it to the output root (where `$relpath^` resolves):

      HTML_EXTRA_FILES  += $(project_directory)/docs/theme/my_logo.png

  Doxygen does **not** scan the header for image dependencies, so a
  header-only image is otherwise never copied (it would 404).
  `IMAGE_PATH` does not help here — it only feeds Doxygen-parsed
  `\image` / markdown references, not raw HTML.  And `HTML_EXTRA_FILES`
  takes individual **files**, not directories (a directory makes
  Doxygen error out and copy nothing). This is exactly how TRUST ships
  its own `theme/ISAS_logo.png`.
- **Custom fonts or analytics.**  Add `<link>` or `<script>` tags
  inside `<head>`, before the existing `$treeview` / `$search` /
  `$mathjax` placeholders.
- **Drop the default Google Fonts import** if you build offline:
  remove the `https://fonts.googleapis.com/...` lines and the
  doxygen-awesome stylesheets will fall back to system fonts.

If your customised header stops working after a Doxygen upgrade in
TRUST, diff against the latest `$TRUST_ROOT/docs/theme/header.html` —
new releases occasionally add new `$…` placeholders that the surrounding
HTML must accommodate.

## Keyword reference

The keyword reference is automatically generated by
[trustify](https://github.com/cea-trust-platform/trustify) and integrated into
the Doxygen output as a searchable, navigable section.

### Structure

The reference is split into one subsection per origin under a **Keyword
Reference Manual** parent page.  For a standalone baltik the layout is:

- **TRUST Keyword Reference** — keyword families inherited from TRUST
- **`<ProjectName>` Keyword Reference** — keyword families introduced by
  the baltik

For a baltik that lists others in `[dependencies]`, every declared
baltik (resolved transitively) also gets its own subpage, e.g. for a
baltik B that depends on A, where A itself depends on Z:

- **TRUST Keyword Reference**
- **`Z` Keyword Reference**
- **`A` Keyword Reference**
- **`B` Keyword Reference**

### How the split works

A single `trustify generate_markdown` run produces the combined keyword
model (TRUST + every baltik in the chain merged) and classifies every
keyword **per class** using the source path stored in `_infoMain` by
trustify.  Origins are derived directly from the project list trustify
resolved — i.e. TRUST plus every baltik discovered transitively from
`project.cfg`'s `[dependencies]`.  Keywords end up in:

- `KW_trust/` family hubs — every keyword whose `_infoMain` is under
  `${TRUST_ROOT}`
- `KW_<dep_name>/` family hubs — one tree per baltik this one depends on
- `KW_<current>/` family hubs — the current baltik's own keywords

When a baltik *extends* an existing family (e.g. adds a new `Source_term_*`
to TRUST's `Source_base`), the baltik-side family hub is a thin page that
lists only the new keywords and `@ref`s the canonical TRUST hub for the
base-class documentation — no content duplication.

The docs/Makefile derives `$project_directory` from the Makefile's own
location (`$(realpath $(CURDIR)/..)`), not from the inherited environment.
This makes the build immune to having sourced the wrong `env_<name>.sh`
beforehand — running `make` from `<baltik>/docs/` always builds that
baltik's docs, even if your shell still has another baltik's env loaded.

> **Note:** classification is per *keyword class*.  Attributes added to a
> TRUST class via `XD_ADD_P` are currently attributed to the class's
> owner, not to the file declaring the `XD_ADD_P` line.  Per-attribute
> attribution is plumbed end-to-end in trustify (`_infoAttr`) and is the
> natural follow-up.


### Standalone generation (without Doxygen)

```bash
make trustify_doc   # generates build/trustify/docs/ (markdown files only)
```

## Using a custom `docs/content/main_page.md`

`docs/content/main_page.md` is written once by `trust -baltik` (or
`trust -baltik_docs_scaffold`) and is **never** regenerated or overwritten
afterwards — edit it freely and commit it to your repository to ship a custom
documentation home page.

A valid `main_page.md` must respect the following rules:

### 1. `@mainpage` directive (required)

The file must contain exactly one `@mainpage` command:

```
@mainpage MyBaltik Documentation
```

Without it, the Doxygen home page will be empty.

### 2. Keyword reference link (recommended)

To include the auto-generated keyword reference in the sidebar navigation, add:

```
@subpage KeywordsReference
```

(`KeywordsReference` is the Doxygen page id emitted by trustify — note the
exact casing; `keyword_reference` is the *file* name and will not resolve.)

Without this line the keyword reference pages are still built and searchable
via the Doxygen search box, but they will not appear in the navigation tree.

### 3. Standard Doxygen Markdown (allowed)

The file may use standard Markdown headings, lists, code blocks, links, and
any Doxygen special commands (`@ref`, `@subpage`, `@note`, `@warning`, etc.).

Hand-written pages other than the home page belong under `docs/content/`,
which the `Doxyfile`'s `INPUT` scans recursively. The template ships a
`docs/content/demo.md` starter page; add your own `.md` files there (each
opened with a `@page <id> <title>` directive) and link them into the
navigation tree from `main_page.md` with `@subpage <id>`.

### 4. Images

`IMAGE_PATH` is empty by default (the shared `doxyfile_common` sets no
directory), so images are not discovered automatically — placing a file
next to `main_page.md` is not enough. To embed an image referenced from
`main_page.md` (or any page under `docs/content/`):

1. Drop the image into a directory of your choice, e.g. `docs/images/`,
   and commit it to the baltik repository so it ships with the project.
2. Add that directory to `IMAGE_PATH` in the `Doxyfile`'s user-override
   block — a commented example ships there:
   `IMAGE_PATH += $(project_directory)/docs/images`.
3. Reference the image by its bare file name.

### 5. Do not edit `Doxyfile.chain`

`docs/Doxyfile.chain` is regenerated on every `make docs` run from
`BALTIK_DEPENDENCIES`. Manual edits are silently discarded. To extend
the C++ API INPUT manually, edit `docs/Doxyfile` (which is generated
once and then left alone).

`docs/Makefile`, `docs/Doxyfile`, `docs/theme/header.html`,
`docs/content/main_page.md`, and `docs/content/demo.md` are all generated
**once** (the Doxyfile by the first `make` in `docs/`, everything else by
`trust -baltik`). They are safe to edit and commit.

## Hooks

Two optional shell scripts are called by `configure` at fixed points:

| File | When called |
|---|---|
| `share/bin/pre_configure` | Before sources are symlinked |
| `share/bin/post_configure` | After all files are generated |

Both scripts receive the same environment as `configure` itself.  A non-zero
exit code aborts the configure run.

## Creating a new baltik from scratch

A minimal template is provided in
`$TRUST_ROOT/bin/baltik/templates/basic/`.  The recommended way to instantiate
it is via `trust -baltik`, which copies the template, expands `@@VAR@@`
placeholders, and runs `baltik_build_configure` for you:

```bash
mkdir my_baltik && cd my_baltik
trust -baltik my_baltik
source env_my_baltik.sh
make optim
```

### Building on top of other baltiks

A baltik can declare that it depends on one or more other baltiks.
Both the build side and the documentation side use the **same source
of truth**: `project.cfg`'s `[dependencies]` section.  Just list each
dependency there:

```ini
# In your project.cfg:
[dependencies]
some_baltik    : /path/to/some_baltik
another_baltik : /path/to/another_baltik
```

That's it.  No second list to maintain, no env-var dance.  See
`baltik_dependencies_management` for details on how the build-side
resolution works at configure time.

For the documentation, `docs/Makefile` queries trustify for the same
list on every `make docs` run:

- `trustify generate_markdown` expands `[dependencies]` transitively
  by itself, so it scans every declared baltik's `src/` for
  `// XD`-tagged classes and emits one keyword-reference subpage per
  origin (TRUST, every declared dependency, this baltik).
- The `Doxyfile.chain` generator queries `trustify projects
  --only=dependency` to extend Doxygen's `INPUT` with each
  dependency's `build/src`, so the C++ API tab covers the full set
  too.

If you need to override the auto-discovered list (e.g. point at an
alternate install of a dependency for a one-off run), set
`BALTIK_DEPENDENCIES` on the command line:

```bash
make BALTIK_DEPENDENCIES="/path/to/alt_dep_a /path/to/alt_dep_b" doxygen
```

The resolution happens inside the `doxyfile_chain` recipe (in
`$TRUST_ROOT/docs/baltik.mk`): if `BALTIK_DEPENDENCIES` is non-empty
it is used as-is, otherwise `trustify projects --only=dependency` is
called. Deferring the call to recipe time guarantees `install_trustify`
runs first, so a fresh checkout without trustify on PATH still
produces a correct `Doxyfile.chain`.

> **Same convention as baltik_configure.**  Trustify's transitive
> resolution mirrors what `baltik_configure` does at build time —
> reading `[dependencies]` recursively, validating that each declared
> `dep_name` matches the dependency's own `[description].name`, and
> raising a clear error on missing paths.  This guarantees the
> documentation list stays in sync with the compiled one: there is
> no second declaration to keep up to date.
